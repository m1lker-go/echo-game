## 4. Использование GitHub и Graphify

Оба инструмента подключены к ChatGPT.

Graphify workspace: Lisovski's workspace.

Репозиторий ECHO проиндексирован Graphify.

Обязательный порядок для значимых изменений:

1. Понять задачу и определить затрагиваемые механики.
2. Найти соответствующие компоненты через Graphify.
3. Проверить зависимости, вызывающие функции и возможные последствия изменений.
4. Найти связанные тесты.
5. Прочитать актуальный код через GitHub.
6. Внести минимально необходимые изменения.
7. Проверить код и доступные тесты.
8. Сообщить пользователю результат.

Graphify не является источником истины о текущем состоянии GitHub: его индекс может отставать от последних коммитов.

При необходимости используй:
- query_graph — исследование логики;
- graphify_callers и graphify_callees — связи вызовов;
- graphify_file_neighbors — зависимости файлов;
- impact_and_risk — статическая оценка последствий;
- graphify_tests_for — поиск связанных тестов;
- recall — ранее сохранённые технические решения.

Graphify не заменяет реальные тесты и проверку поведения игры.

Не создавай фиктивных отчётов о проверках. Если тесты не запускались, так и скажи.

## 5. Общая архитектура ECHO

ECHO — отдельная многопользовательская браузерная игра с изометрическим игровым миром, 3D-персонажами, PvP, экономикой, коллекцией персонажей, магазином, заданиями и аккаунтами.

Игра рассчитана на горизонтальную ориентацию экрана.

Основные компоненты:

Frontend:
- HTML;
- CSS;
- JavaScript;
- Canvas;
- 3D-модели GLB;
- отдельные JavaScript-модули игровой логики и интерфейса.

Backend:
- Node.js;
- Express;
- Socket.IO;
- PostgreSQL.

Основные директории:
- client/ — интерфейс и игровой клиент;
- server/ — API, игровые механики, аккаунты, платежи;
- shared/ — общая логика;
- server/test/ — автоматизированные тесты;
- .github/workflows/ — CI/CD.

Не заменяй существующую архитектуру на другой фреймворк без согласования.

## 15. Android APK

Для ECHO разрабатывается отдельное Android-приложение.

Работа ведётся также через Android Studio.

Android-версия предназначена для горизонтального экрана и должна использовать существующую инфраструктуру ECHO.

В предыдущей работе использовались Android WebView, отдельные нативные элементы и интеграции авторизации.

Существуют разные особенности:
- запуск из браузера;
- запуск через VK Mini Apps;
- запуск Android APK.

Нельзя считать, что все три среды ведут себя одинаково.

В проверенном состоянии ветки main от 25.10.2026 папка android отсутствовала. Поэтому перед изменениями Android необходимо установить, где находится актуальный Android-проект: в другой ветке, локально в Android Studio или в отдельном источнике.

Не выдумывай структуру Android-проекта.

Для Android OAuth может использоваться системный браузер и возврат через deep link.

Не помещай клиентские секреты OAuth в APK.

### Подписание Android-приложения

Особо важное правило:

НИКОГДА не создавай новый релизный keystore и не заменяй существующий ключ подписи без прямого согласования.

## 20. Работа с кодом — обязательные правила

Правило №1: сначала исследуй, потом меняй.

Правило №2: предпочтение минимальным изменениям.

Правило №3: не удаляй существующие механики ради упрощения.

Правило №4: не меняй посторонние файлы.

Правило №5: не переписывай большие файлы целиком, если достаточно локального исправления.

Правило №6: перед изменением учитывай зависимости через Graphify и актуальный код GitHub.

Правило №7: после изменений проверяй связанные системы.

Правило №8: если пользователь просит только анализ, не изменяй файлы.

Правило №9: если пользователь прямо просит внести изменения, можешь выполнить их через подключённый GitHub без дополнительного формального подтверждения, кроме потенциально разрушительных и критичных действий.

Правило №10: не выдавай предположение за подтверждённый результат.

Запрещены без отдельного согласования:
- force push;
- удаление веток;
- уничтожение таблиц БД;
- изменение существующего релизного ключа;
- изменение секретов;
- массовые рефакторинги вне задачи;
- отключение тестов ради успешного деплоя;
- удаление рабочих функций без замены;
- изменение конфигурации Cat Fighting.

## 21. Тестирование

В ECHO существует набор автоматизированных тестов в server/test/.

Основная команда:
npm test

Запускать из директории server/.

Перед изменениями проверяй, какие тесты охватывают затрагиваемые системы.

После изменений по возможности выполняй:
- проверку синтаксиса;
- связанные тесты;
- полный набор тестов;
- проверку GitHub Actions;
- проверку деплоя;
- ручное тестирование нужной платформы.

Если выполнение тестов невозможно через доступные инструменты, сообщай об этом честно.

При ошибках GitHub Actions исследуй логи и исправляй причину, а не просто повторяй деплой бесконечно.

## 22. Как общаться с пользователем

Пользователь предпочитает практическую разработку, а не длинные теоретические объяснения.

Если можно выполнить действие самостоятельно через GitHub или Graphify — выполняй, когда это входит в задачу.

Не проси пользователя искать файлы, которые доступны тебе через инструменты.

Не заставляй пользователя вручную копировать код, который можешь безопасно отредактировать сам.

При работе через Android Studio объясняй шаги последовательно и указывай точные пути и команды после проверки.

После выполнения задачи кратко сообщай:
- что изменено;
- какие файлы затронуты;
- что проверено;
- результат тестов;
- коммит и состояние деплоя, если применимо;
- что должен проверить пользователь.

Если задача сложная, самостоятельно исследуй необходимые файлы и связи. Не требуй от пользователя заново описывать известную архитектуру.
